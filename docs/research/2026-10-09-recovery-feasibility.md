# Recovery cryptography feasibility (2026-10-09)

**Decision:** `serenity-kit/react-native-libsodium` is the strongest single binding candidate found for Finance Bro’s selected libsodium APIs: it has native JSI implementations for Argon2id and XChaCha20-Poly1305 plus a React Native Web path to libsodium.js WASM. Its API fit is good enough for a bounded integration spike, but **the binding/source-build gate is not cleared**. The published native package extracts prebuilt libsodium binaries, its own source-build script still pins libsodium 1.0.21-stable, and its example targets React Native 0.83 while this app is on Expo SDK 58 / RN 0.88. Do not freeze the backup format or add the runtime dependency until source-built Android and exact SDK58 native compatibility are demonstrated.

This note addresses feasibility for [#42](https://github.com/Starforge-lab/finance-bro/issues/42) against the F-Droid source-build requirement in [#56](https://github.com/Starforge-lab/finance-bro/issues/56). It is research, not an implementation decision to ship the dependency.

## Candidate and API evidence

The app currently uses Expo `~58.0.6`, `expo-sqlite ~58.0.10`, and `react-native 0.88.0-rc.3` ([mobile package manifest](../../apps/mobile/package.json)). Expo’s SDK 58 reference maps SDK 58 to RN 0.88. The candidate README documents Android, iOS, and web; an Expo config plugin; and a New Architecture example, but that example follows RN 0.83 defaults. The candidate declares broad React/RN peer ranges, which is not proof it builds against RN 0.88. The native compatibility edge therefore remains unverified. [Expo SDK 58 reference](https://docs.expo.dev/versions/v58.0.0/) · [candidate README](https://github.com/serenity-kit/react-native-libsodium/blob/main/README.md) · [candidate package manifest](https://github.com/serenity-kit/react-native-libsodium/blob/main/package.json)

| Runtime | Concrete API path | Evidence and limits |
| --- | --- | --- |
| Android/iOS | `crypto_pwhash(keyLength, password, salt, opsLimit, memLimit, crypto_pwhash_ALG_ARGON2ID13)` and `crypto_aead_xchacha20poly1305_ietf_encrypt/decrypt` | The native TypeScript surface declares the Argon2id constant and JSI functions. The C++ host function calls libsodium `crypto_pwhash()` with the supplied algorithm, salt, ops and memory limits; separate host functions call XChaCha encrypt/decrypt. These calls are synchronous JSI host functions, so KDF latency and UI-thread blocking need measurement on actual native builds/devices. [native TypeScript bindings](https://github.com/serenity-kit/react-native-libsodium/blob/main/src/lib.native.ts) · [native JSI implementation](https://github.com/serenity-kit/react-native-libsodium/blob/main/cpp/react-native-libsodium.cpp#L1002-L1068) · [XChaCha implementation](https://github.com/serenity-kit/react-native-libsodium/blob/main/cpp/react-native-libsodium.cpp#L1143-L1216) |
| Web | `loadSumoVersion()` before awaiting `ready`, then `crypto_pwhash` and XChaCha exports from `libsodium-wrappers-sumo` | The package’s web implementation delegates to libsodium.js wrappers; the standard build omits `crypto_pwhash_*`, while the Sumo build includes them and contains WebAssembly plus a JavaScript fallback. The main wrapper documentation reports Sumo at about 375 KB minified/gzipped including WASM and fallback. [candidate web README section](https://github.com/serenity-kit/react-native-libsodium#react-native-web) · [libsodium.js standard/Sumo and WASM docs](https://github.com/jedisct1/libsodium.js#standard-vs-sumo-version) |

There is a documentation inconsistency worth resolving in the spike: candidate README import comments label `crypto_pwhash` and its constants “only with loadSumoVersion with react-native-web”, yet native TypeScript and C++ source expose and implement `crypto_pwhash` and `crypto_pwhash_ALG_ARGON2ID13`. This report relies on the native code as evidence of an implementation, not as evidence that an SDK58 build works. Add native and web tests against the exact installed package before relying on this split API.

The native XChaCha adapter also has a narrower runtime contract than its public TypeScript signature: the signature allows `string | Uint8Array | null` additional data and a string ciphertext, but the implementation throws “input type not yet implemented” for non-string additional data and for string ciphertext on decrypt. Use a fixed UTF-8 string for archive AAD and byte-array ciphertext in a shared adapter, or require an upstream correction; test the native and web paths with the same deterministic vector. Without that restriction/fix, the advertised cross-platform API is not equivalent. [native XChaCha adapter](https://github.com/serenity-kit/react-native-libsodium/blob/main/src/lib.native.ts)

The official libsodium guidance recommends XChaCha20-Poly1305 where cross-library interoperability is not required; it permits random 192-bit nonces but forbids reuse of a nonce with the same key, authenticates optional additional data, and rejects invalid authentication tags. Store the archive-format/version context as AAD and generate a fresh nonce per archive. Argon2id requires persisting the algorithm and exact ops/memory parameters with the salt so the same key can be derived later. The interactive baseline uses 64 MiB; choose and benchmark parameters as a user-facing recovery contract, not as unversioned constants. [XChaCha construction](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction) · [libsodium password hashing](https://doc.libsodium.org/password_hashing/default_phf)

### Isolated WASM check

A temporary directory outside the repository installed `libsodium-wrappers-sumo@0.8.4`. A Node smoke test instrumented `WebAssembly.instantiate` and asserted it was called, derived a 32-byte key using Argon2id with the interactive limits and a fictional password, encrypted/decrypted a fictional payload with XChaCha20-Poly1305 and AAD, and asserted a tampered ciphertext was rejected. All assertions passed, with one WASM instantiation observed. No Finance Bro dependency or lockfile was changed. This verifies the standalone wrapper’s Node/WASM path; it does **not** verify Expo Metro bundling, a real browser, the candidate’s package integration, or native code.

## Source-build and license gate

The candidate is MIT licensed and identifies the copied libsodium.js helper license separately. Libsodium and libsodium.js wrappers are ISC licensed. Those licenses are permissive, but #56 still requires auditing the complete locked runtime tree and retained notices before release. [candidate license](https://github.com/serenity-kit/react-native-libsodium/blob/main/LICENSE) · [libsodium license](https://github.com/jedisct1/libsodium#license) · [libsodium.js license](https://github.com/jedisct1/libsodium.js/blob/master/LICENSE)

The default native package is **not currently a clean source-build path**:

- Its npm package includes `libsodium/build.tgz`; `postinstall` extracts it. The CocoaPods `prepare_command` also extracts that archive when generated frameworks are absent. Android CMake links `libsodium.so` from the extracted build directory. [package files and postinstall](https://github.com/serenity-kit/react-native-libsodium/blob/main/package.json#L502-L566) · [podspec](https://github.com/serenity-kit/react-native-libsodium/blob/main/react-native-libsodium.podspec) · [Android CMake](https://github.com/serenity-kit/react-native-libsodium/blob/main/android/CMakeLists.txt)
- The repository does provide `libsodium/build.sh`: it downloads `libsodium-1.0.21-stable.tar.gz`, verifies the minisign signature using the included upstream public key, then cross-builds Android ABIs (and an iOS XCFramework on macOS). However, this script fetches over the network and packages its generated binaries into `build.tgz`; it is not what normal app installation invokes. [build script](https://github.com/serenity-kit/react-native-libsodium/blob/main/libsodium/build.sh)
- Upstream libsodium now publishes `1.0.22-stable` (2026-10-07), while the candidate’s checked-in script remains pinned to `1.0.21-stable`. The binding repository and npm package last moved on 2026-02-09. Treat this as a maintenance/version-refresh risk, not evidence of an upstream security defect. [official release index](https://download.libsodium.org/libsodium/releases/) · [candidate repository activity](https://github.com/serenity-kit/react-native-libsodium/commits/main)
- F-Droid’s current inclusion policy says binary dependencies must come from source compilation or Debian repositories, subject to its documented exceptions. Its metadata supports pinned source libraries and a build phase for commands that produce binaries. A viable route is to remove/ignore the shipped `build.tgz` in the F-Droid recipe, provide a pinned and signature-verified libsodium source input to the offline build, compile the Android libraries with the configured NDK during the build phase, link only those outputs, and run the clean F-Droid build plus license/reproducibility checks. No such recipe or build was tested here. [F-Droid inclusion policy](https://f-droid.org/en/docs/Inclusion_Policy/) · [F-Droid build metadata](https://f-droid.org/en/docs/Build_Metadata_Reference/) · [libsodium signed source release](https://download.libsodium.org/libsodium/releases/)

So the candidate has a plausible source route, but its current published install path fails the F-Droid gate. The route is only proven after the recipe builds from pinned source without the prebuilt archive and the produced app passes the actual F-Droid build/scan. If that is not maintainable, choose or develop a different binding before format freeze; do not waive the release gate.

## Restore integration hazards in the current app

- **Native fingerprint key:** [`fingerprint-store.native.ts`](../../apps/mobile/src/imports/fingerprint-store.native.ts) reads a 32-byte HMAC secret from SecureStore and generates/stores a new key when absent. The export/import API is private to the provider today; no method restores archived key material through SecureStore. SQLite stores only the public key ID in [`import_key_state`](../../apps/mobile/src/db/schema.ts). [`requiresDuplicateReview`](../../apps/mobile/src/imports/key-state.ts) compares this marker with the active key ID, so replacement keys are detected at the paste flow, but silent key creation itself does not meet #42’s “no silent key regeneration” criterion. Recovery needs an explicit missing/restored-key state and a guarded key-write path.
- **Web fingerprint key:** [`fingerprint-store.web.ts`](../../apps/mobile/src/imports/fingerprint-store.web.ts) stores a nonextractable WebCrypto HMAC `CryptoKey` in IndexedDB and creates one if missing. Preserve same-origin key reuse. Do not serialize/export this CryptoKey into the backup; a fresh origin necessarily gets a different key and needs a recorded key epoch plus duplicate-review gate while retaining restored transaction IDs and tombstones. The current `import_key_state` schema only has one `key_id`, not an epoch or restore state.
- **Ledger replacement:** [`db/index.ts`](../../apps/mobile/src/db/index.ts) memoizes one `DataLayer` over an open `finance-bro.db` connection. The low-level client type in [`db/ledger.ts`](../../apps/mobile/src/db/ledger.ts) exposes `withTransactionAsync`, not an exclusive transaction or database-swap operation; migrations use the nonexclusive method. Expo SDK 58 documents `withExclusiveTransactionAsync` only for native platforms, and says it is not supported on web; `withTransactionAsync` is nonexclusive and can be interrupted by other async queries. Expo also supports WAL, so replacing/renaming a database file while its connection remains live is a hazard by inference, not a tested failure. Stage and fully validate a restore in a separate database, then replace records through a coordinated transaction on the existing connection, gating concurrent app writes across the operation. Native can use its exclusive transaction API if all transaction queries use the provided `txn`; web needs an app-level serialized write gate or another tested atomic approach. [Expo SQLite SDK 58 transaction and import docs](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/)
- **Imported state:** [`db/schema.ts`](../../apps/mobile/src/db/schema.ts) contains accounts, categories, budgets, bills, transactions and `import_key_state`; there is no preferences table yet. Transactions carry parser provenance, `userEdited`, `deletedAt` tombstones, foreign-key relationships and positive safe-integer-paise constraints. [ledger contract](../ledger.md). Restore validation must include all of these fields/relationships and preserve deleted rows; do not treat a visible-row export as a full backup. The exact backup entity set still needs reconciling with #42 as preferences and any future import-provider metadata are added.

## Gate sequence before implementation or format freeze

1. Pin an exact `react-native-libsodium` source revision and resolve the stale README/API discrepancy. Build its example or a minimal Expo SDK58 app with this repository’s RN 0.88 / New Architecture; exercise Argon2id and XChaCha on Android and iOS. Compare deterministic test vectors across native and web, then measure KDF latency/memory and ensure the user-triggered KDF does not freeze the UI. A build alone is not runtime/device verification.
2. Confirm Metro emits and serves the Sumo WASM asset in the production web export, initializes `loadSumoVersion()` before use, and passes browser tests under the app’s COOP/COEP headers. Expo documents WASM and cross-origin-isolation setup, and this app already configures those headers in [`app.config.ts`](../../apps/mobile/app.config.ts); integration remains untested. [Expo SQLite SDK 58 web requirements](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/#web-setup)
3. Make an F-Droid build use pinned libsodium 1.0.22-stable source with signature verification and no bundled `.so`/XCFramework input; run the clean F-Droid recipe and its dependency/license/reproducibility checks. Keep the npm/web wrappers’ ISC notices and the native module’s MIT notice.
4. Only after those gates pass, define the archive envelope and then implement the #42 temporary-database validation, atomic apply, native key restore, same-origin/fresh-origin semantics, wrong-password/tamper/truncation/interruption/newer-schema tests, and user-facing password/destination warnings.

## Evidence and limits

- Repository inspection was against `origin/dev` commit `2737b6531fd1dcc6dca10d28c9253acca2a4ff22`; no repository packages were installed or manifests/lockfiles changed for this research.
- The standalone Sumo WASM Node assertions described above passed using fictional bytes only.
- No native module install/build, Expo SDK58 web export/browser test, physical device run, F-Droid clean build, or full transitive license audit was performed. Native runtime behavior and release eligibility remain unverified.
